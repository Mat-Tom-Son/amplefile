# AmpleFile contributor guide

AmpleFile is a local-first Electron shell around ordinary folders and the native Pi agent runtime. Read [the product model](docs/product-model.md) before changing navigation, terminology, storage, trust, or Worker behavior, read [the App platform foundation](docs/app-platform-foundation.md) before changing App Project, release, instance, Feature, publication, hosted-runtime, data, connection, automation, or broker semantics, read [the AmpleFile agent and CLI](docs/amplefile-agent-and-cli.md) before changing the kernel, CLI, task registry, or an agent-facing adapter, read [Checks](docs/checks.md) before changing Check declarations, sensors, targets, evidence admission, decisions, or run authority, read [the AmpleFile agent decision register](docs/amplefile-agent-decisions.md) before changing the AmpleFile agent's verb ledger, prepared acts, Recently deleted, Automations, or the overview, read [Receipts, not gates](docs/receipts-not-gates.md) for the 2026-09-10 authority decisions that register now carries, and read [the collaboration contract](docs/collaboration-contract.md) before changing durable requests, delegation, questions, results, waiting and continuation, or an app's owned-change hints. These documents record the shared product and control-plane direction; update them when those decisions change.

## First visit

- Start with [Contributing](CONTRIBUTING.md) and the [development guide](docs/development.md) for setup, a source map, development profiles, and the right verification lane.
- Use Node 24 and npm 11.16.0 or newer for the contributor/CI lane (`.nvmrc`); npm must enforce the dependency-script policy described in [Contributing](CONTRIBUTING.md#first-run). Run `npm ci`, then `npm run repo:check`; the latter also works before installation and never needs credentials or a network connection.
- `npm run local:dev` starts the browser UI and local API; `npm run desktop:smoke` starts unpackaged Electron after preparation. Use disposable folders for live work. The development app profile is separate, but Pi resources and Keychain require their own consideration; follow the development guide for explicit isolation.
- `npm run check` includes repository hygiene and TypeScript checks. Keep new shared Skills, Claude symlinks, links, and documented npm commands valid; do not copy shared policy into a harness-specific file.

## Harness parity

- This `AGENTS.md` is the one canonical contributor contract. Codex reads it directly; Claude Code reads the root `CLAUDE.md`, which imports this file with `@AGENTS.md`.
- Edit shared policy here instead of copying it into `CLAUDE.md`, `.claude/`, `.codex/`, or harness-specific prose. Keep the root Claude entrypoint thin so the two harnesses cannot drift.
- Project-wide Skills have one source under the tracked `.agents/skills/` directory. Codex discovers that source directly; Claude Code gets the same Skill through tracked `.claude/skills/` symlinks. Never copy Skill contents between the two trees. All other `.claude/` and `.codex/` files are machine-local harness state, not contributor contracts.
- Both harnesses use the same checked-in npm scripts, documentation, test suites, and release lanes. Do not create alternate Claude-only or Codex-only build or release commands.
- Native full-trust Skills, Extensions, built-in tools, and their catalog/runtime remain Pi-owned. AmpleFile owns the product documentation and restricted-app lane, but both remain harness-neutral. Do not create a Codex-only or Claude-only catalog, wrapper format, prompt copy, or tool policy.
- `amplefile <command> --json`—for example, `amplefile context --json`—is the stable installed-product surface for any shell-capable harness: a content-free read lane plus a per-launch-authenticated act lane (`chat`, `chats`, `agent`, `history`, `files`, `search`, `connected-folders`, `tools`, `apps`, `checks`, `automations`, `pages`, `recently-deleted`, `requests`, `jobs`, `worktrees`) that needs the running app. Every act verb executes on first call and returns a receipt; the lane has no approval, waiting, or authority-mode state. A task may still be *waiting on an answer* — that is a state of its request record, not a held verb, and `chat wait`/`agent wait` settle on it and say so. `checks status` alone stays in the content-free read lane; Check enablement, runs, results, problems, and decisions are act-lane operations over explicitly designated files. The `agent` group talks to the AmpleFile agent above all Connected Folders: machine-local transcript, Everywhere capabilities plus app-materialized instructions, same turn machinery, full-trust (taught to prefer the CLI, not tool-restricted). `npm run amplefile:drive` is the separate real-Pi-turn test driver; do not conflate it with the installed `amplefile` CLI.
- `npm run --silent amplefile:appearance` is the shared Codex/Claude Code primitive for creating, resolving, and validating inert connected-folder-appearance proposals. It never applies a mutation; the person imports the typed file in Customize Connected Folder. Separately, `amplefile connected-folders appearance apply|reset|undo` is the act lane's journaled, undo-carrying application path for the same typed proposal while the app is running; the npm-script primitive stays inert and import-only. Keep its schema and safety boundary aligned with [Connected Folder customization](docs/connected-folder-customization.md).
- [Development](docs/development.md#agent-setup-and-shared-skills) links the Codex and Claude Code harness-loading docs. Repository behavior is defined here.

## Product language and boundaries

The interface's words are also the code's: identifiers, HTTP routes, CLI
verbs and flags, JSON keys, schemas, and storage paths say **Connected
Folder** (`connected-folder`, `connectedFolder`; the folder-backed working
context), **Worker** (its AI assistant), **AmpleFile agent**
(`amplefile-agent`; the agent above all Connected Folders), **Automation**
(deterministic cross–Connected Folder steps), **Recently deleted**, and
**overview** (the AmpleFile agent's digest). Labels are Title Case, and
"Connected Folder" is capitalized everywhere, like "Worker"; an ordinary
directory on disk stays a plain "folder". [The vocabulary
glossary](scripts/vocabulary/GLOSSARY.md) lists the exceptions: opaque
`space-<16 hex>` ids, the app-state `spaces/` and `management/` folders,
and the restricted-app `assistant.*` bridge API. Do not rewrite dated quotations. An Automation runs reviewed, fixed steps on its declared
trigger; it is not an open-ended Worker scheduler or an app automation.

- Use **AmpleFile** as the user-facing product name.
- A **Connected Folder** is a human-friendly working context backed by one ordinary folder. Registering an existing folder must not move, copy, or rename user files. AmpleFile deliberately maintains hidden, portable `.amplefile/connected-folder.json` identity metadata and `.amplefile/conversations/` logs in that folder.
- The folder is transparent infrastructure, not a proprietary container. Keep **Show folder** and normal filesystem interoperability intact.
- There is no **Web Access** and no page **Publish** (removed 2026-11-07): the desktop never connects to a hosted bridge or page service; those stayed with the work-fold repository.
- There is no **Library** (desktop surface removed 2026-09-25; CLI family, `/api/resources` routes, and code 2026-10-10; an existing app-state `resources/` folder is left untouched). Do not describe it as a product surface or an Add destination.
- Use **Skills & Extensions** — the popup dialog the Action menu's **Skills & Extensions…** opens — as the user-facing management surface and **Capability** as the internal umbrella. Inside it, use **Skill** for a reusable way of working and **Extension** for executable Pi capabilities or connections. Packages are distribution and lifecycle plumbing, not another top-level product concept.
- Treat `src/shared/product-identity.json` as the single brand-bearing identity contract. The product is `AmpleFile`, the package is `amplefile-desktop`, the production app id is `com.amplefile.desktop`, the local-smoke app id is `com.amplefile.desktop.local-smoke`, the updater cache is `amplefile-desktop-updater`, the internal scheme is `amplefile-desktop`, the CLI is `amplefile`, and product-owned environment variables use `AMPLEFILE_*`.
- New product-facing technical contracts use `/api/connected-folders`, `/api/amplefile-agent`, `x-amplefile-session`, `window.ampleFileDesktop`, `amplefile.restricted-app-bridge`, and `globalThis.ampleFileRestrictedApp`. App-platform records use `amplefile.app-release`, `amplefile.artifact.v1:sha256:*`, `application/vnd.amplefile.*`, and the identity fields `connectedFolderId`, `sourceConnectedFolderId`, and `targetConnectedFolderId`; do not accept the legacy spellings as aliases.
- Keep provider credentials, Connected Folder registrations, History objects, Pi sessions, ignore rules, and machine-specific application state outside user content folders. Only the documented portable `.amplefile/` records belong in a Connected Folder.
- Treat project Pi resources—including `.pi` and other Pi-supported project locations—as executable configuration. Successfully creating or registering a Connected Folder is AmpleFile's authorization to load that folder's local Pi configuration; removing the Connected Folder revokes that AmpleFile authorization. Do not add a second trust prompt for the same act.
- Prefer Pi's built-in tools, resource loader, auth storage, model registry, package manager, skills, and extensions over app-specific replacements.
- [Extensions and computer work](docs/extension-foundation.md) records the shared integration design and inclusion requirements. Native Pi UI callbacks are transient, Chat-scoped interactions; never claim durable F27 continuation for a suspended callback, or auto-answer an Extension's confirmation. Included capabilities must use a supported path available to other Extensions too.
- Keep agent-created restricted apps in their separate reviewed-web lane. They use `agent-app.json`, digest-pinned installation, sandboxed Electron hosts, and narrow host brokers; they must never be installed through Pi's package manager or merged into Pi's loaded Extension catalog.
- Do not bundle proprietary tools, instructions, or source libraries.
- Do not describe a desktop-synchronized folder as native cloud integration. Google Drive currently works through Google Drive for desktop; direct Drive APIs and native provider OAuth are future adapter work.

## Product rails

- **Local first:** a Connected Folder remains useful as a folder without an account or cloud service.
- **Understandable:** explain outcomes in terms of Connected Folders and Skills & Extensions; identify Skills and Extensions inside that popup, and reveal technical paths and package sources as supporting detail.
- **Explicit context:** registering a Connected Folder, adding or copying materials, installing packages, granting connections, and attaching files are distinct actions. Do not silently put files or capabilities into a conversation.
- **Understandable authorization:** creating or registering a Connected Folder authorizes its local Pi configuration without a redundant trust ceremony. Package review, connection secrets, and Chat context remain separate explicit acts; installing a Connected Folder app grants the powers its package declares ([Receipts, not gates](docs/receipts-not-gates.md), F21); and removing the Connected Folder must revoke AmpleFile's project-runtime authorization.
- **Portable identity:** `.amplefile/` is data, not executable configuration. Preserve a valid manifest id when a Connected Folder's folder moves, hide `.amplefile/` and `.pi/` from Files, and exclude both from History capture.
- **Clean break:** AmpleFile never parses, imports, migrates, mutates, or deletes legacy Workspace application state or `.workspace/` metadata. Legacy metadata remains hidden and excluded from Files, History, Search, Check targets, and restricted-app grants, but it is non-authoritative. Managed deletion moves the claimed folder into Recently deleted rather than erasing it, and an entry whose tree contains `.workspace/` is held there: neither the retention window nor **Delete now** may erase it. Registration removal remains available without folder deletion. A new AmpleFile profile starts empty; Pi's global resources and auth may remain shared at the configured Pi root, while AmpleFile sessions use their own `sessions/amplefile/` namespace.
- **Connected Folder–bound Chats:** every Chat belongs to one Connected Folder, and the Worker panel shows the Chats of the Connected Folder shown. Never make a Chat silently inherit whichever Connected Folder happens to be selected.
- **Background continuity:** a Chat's accepted turn keeps running while another Chat or folder is shown. Switching, taskbar minimization, sleep/wake recovery, and close-to-tray must not cancel an accepted turn or lose its persisted result; only an explicit stop or quit may do that.
- **Settled deletion:** file, Chat, and Connected Folder deletion refuse while affected request work is unfinished, waiting on an answer, or still draining after Stop. File and Connected Folder deletion hold the shared active-work reservation through the effect. Managed parent deletion requires removing nested Connected Folder registrations first; pending deletion rejects new descendant registrations. Never bypass a busy refusal with raw tools.
- **Native Pi compatibility:** preserve standard `SKILL.md` directories and Pi scopes. Do not fork an AmpleFile-only skill or extension format.
- **General computer work:** avoid code-only assumptions in primary UI copy and workflows.
- **Apps come up able to work:** installing a preview or a Release grants every declared network destination, file permission (a directory permission binds to the whole Connected Folder), notification category, and Check-result slot, and enables every declared automation; a code change carries forward connections whose destination declaration is byte-identical, automation enabled states by id, and run receipts. Revoke, disconnect, and disable are the person's narrowing controls, and revocation must stop stale launches before authority changes take effect. Secrets are entered by the person once per destination on the trusted surface; no task waits on that.
- **Receipts, not gates:** every product verb executes on first call and leaves a receipt. Verbs that make bytes runnable, widen a standing power, or destroy still pin their exact identities, journal before execution, recheck at effect time, execute at most once, and run through the same domain path as the desktop — as attribution and recovery, not as a gate. There is one authority mode and no approval card, standing rule, or toggle. Every destruction is reversible: History covers what it can, and everything it cannot goes to machine-local Recently deleted with a retention window. Provider-secret entry remains a setup surface rather than a model/CLI verb, and no task waits on it.
- **Requests, questions, and one result shape:** every accepted Worker or AmpleFile agent turn belongs to a durable machine-local request record ([the collaboration contract](docs/collaboration-contract.md), F25). Agents hand each other one result shape — a plain-language summary, optional structured details, the files they chose, and an outcome of succeeded, partial, or failed — and ask a question instead of guessing. A question ends its own turn and one accepted answer continues it exactly once; a parent turn never sits on a child that is waiting, and the host starts at most one follow-up turn per settle batch within the request's limits. The same verbs serve the AmpleFile agent, a Worker, an app's requested task, and any shell-capable agent on the CLI, with the same receipts and the same named limits. Request records never enter a Connected Folder: what reaches a Worker Chat is its assignment, answers to its own questions, deliberately released payloads, and copied files.
- **Cadence above Connected Folders:** agency on a schedule lives in Connected Folders. Above them, only declared deterministic Automations run unattended (including explicitly enabled bounded folder-change triggers; see [Automations](docs/automations.md)). `automations enable` is one receipted call that pins the declaration digest; an Automation may also message the AmpleFile agent through its declared `agent` step and fill a closed set of host-resolved placeholders. Cross–Connected Folder work never runs inside a Worker Chat because Connected Folder transcripts travel; what enters a Worker Chat from above is its assignment, explicitly released payloads, and answers to its own questions.

## Stable information architecture

The window is the file manager ([product model](docs/product-model.md#2026-11-06-file-manager-layout); the classic rail-and-tabs layout was removed on 2026-11-07, and there is no Layout setting): a sidebar of **Standard Folders** and **Connected Folders** (nested ones indented under their parent), a Finder-style toolbar, contents, and path bar, and the Worker panel with its **Info** and **History** tabs and the message box. The toolbar's **Action** (⋯) menu and a Connected Folder's right-click menu offer Customize Connected Folder, Set Up for Me, Just the Look, Show in Finder, **Skills & Extensions…**, and **Settings…**; **Shortcut Keys** lives in Settings. There is no Library, no Agent tools tab, no page or browser tab, and no in-window app view. Skills & Extensions is a popup dialog like Settings, pinned to the Connected Folder it was opened from, with Installed and Discover views; package source, scope, type, load state, diagnostics, update, and removal remain visible inside it. Its Installed view starts with an **Included with AmpleFile** strip holding exactly the five included tools — Chrome, Computer Control, Web, Documents, and Service Connections — each with one concise Title Case status (Ready, Setup Needed, Unavailable, Not Checked, or Turned Off, with the per-tool variants in the [product model](docs/product-model.md)) and a **Set Up** pointer only when a person can act. Below the strip, **Everywhere** (the AmpleFile agent and every Connected Folder) and **This Connected Folder only** (stored in the Connected Folder) sit side by side and stack on narrow widths; a row opens its details on click, and the groups have no Add buttons. The popup's Add dialog asks **Where should it live?** first with the same two-card chooser, then offers a Skill or pack (files) or a Pi package (source). A Discover details dialog shows the description, the where-chooser, the Skills and Extensions inside, one plain warning when the install can run code on the computer, and a collapsed **Technical details** section (source, version, license, provenance, dependencies, install scripts); install scripts and Extensions are still disclosed before installation. Installed Connected Folder apps have no view in the window; **Settings → Apps** lists apps by Connected Folder and owns each app's grants, connections, named automations and run history, local data, update review, removal, Worker requests, and the receipts of the app's model use; there is no **Build with Worker** button — a person asks a Worker to build an app in a Chat. Model-provider connections, model selection, API-key, and provider-OAuth setup belong in **Settings → AI Models**; its scope is chosen with two large buttons — **This worker**, naming the Connected Folder, and **AmpleFile agent** — and its model is a searchable dropdown grouped by vendor ([product model](docs/product-model.md), 2026-09-27). Provider credentials are machine-wide, while model selection is saved separately for each portable Connected Folder identity and for the AmpleFile agent, whose choice applies in the menu bar and on the web too. App connection grants and OAuth setup belong with that app in Settings → Apps. Settings → Automations keeps its limits under a **Limits** disclosure, collapsed by default and unchanged in meaning. User-facing copy uses **Connected Folder**, **Worker**, **AmpleFile agent**, **Automation**, **Skills & Extensions**, and **Recently deleted**; internal types may still use `project`, `resource`, or `capability` as technical terms.

See [Skills & Extensions](docs/skills-and-extensions.md) for the scopes, trust model, Anthropic-compatible skill import behavior, package boundary, and the layout of the Skills & Extensions popup.
Read [Restricted app runtime](docs/restricted-app-runtime.md) and [Restricted app authoring](docs/restricted-app-authoring.md) before changing `agent-app.json`, app proposals, sandbox hosts, bridges, brokers, credentials, storage, notifications, named automation scheduling, or contributed app navigation.

## AmpleFile agent and CLI

- `AmpleFileKernel` is the shared in-process read authority for versioned Connected Folder context, registered Connected Folders, active turn and compaction tasks, and Pi capability snapshots. The renderer/local API and CLI must consume the same semantic source rather than recreate selection or catalog rules.
- Every query carries an explicit actor. An explicit Connected Folder id wins; otherwise context resolves to the deepest registered Connected Folder containing the actor's current directory; otherwise it resolves to none.
- Keep adapters thin. The CLI projection intentionally emits compact, content-free summaries, while domain services continue to own mutations, trust, filesystem policy, History, and concurrency controls.
- Protocol v1 under `%APPDATA%\AmpleFile\cli` is same-user coordination, not an authenticated caller boundary. It must remain read-only and content-free. Mutations belong exclusively to the separately versioned act lane, which requires the per-launch act token minted by the running interactive app, explicit `--connected-folder` selection on every Connected Folder–scoped write (the `agent`, `automations`, `recently-deleted`, and `requests` families are deliberately Connected Folder–free; a Recently deleted entry records its source Connected Folder, and a request record pins the Connected Folder of each child at the moment that work is handed over), replayed-request protection, and a durable receipt per accepted action; keep those properties intact when extending it. Runnable-code, standing-power, and destruction verbs run immediately through the prepare, pin, journal-first, fenced execution path and return the receipt like any direct verb; failed or interrupted executions are never auto-retried; destruction is reversible through History or Recently deleted. The act facade cannot enter secrets. Act-token machinery and provider credentials remain setup-only and have no act verb.
- Start and finish kernel task records on every turn and Chat-compaction path, including errors and abort cleanup. Never leave ghost tasks or let a capability mutation interrupt active work.
- The AmpleFile agent's menu-bar/tray popover is a separate sandboxed renderer with a dedicated narrow preload. Its attachments are bounded references, not copies; downstream `chat.send`, `files.add`, and Connected Folder create/register actions carry an explicit active AmpleFile agent parent task id. Never infer request lineage from whichever turn happens to be running, and never report a request Done while a child is running, waiting on an answer, failed, lost, or stopped.
- Every accepted turn joins one durable request record under the state root's `requests/` directory — not an in-memory registry. Records survive restart, are reconciled against the turn journal and never re-dispatched, keep their questions and results by id, and are removed only by retention. `requests list|show` reads that graph; `chat report|ask|answer|handoff` write to it; `chat wait`/`agent wait` settle when the followed turn ends or when its task starts waiting, and say which. Delivery of a report, an answer, or a handoff is host-side and needs no AmpleFile agent turn.
- Treat snapshot versions and `--json` output as compatibility contracts. Update implementation, adapters, tests, [the AmpleFile agent and CLI guide](docs/amplefile-agent-and-cli.md), README, security, and privacy documentation together when they change.

## Development

- Develop with Node 24 and npm 11.16.0 or newer; the package runtime floor stays Node 22.19.0.
- Run `npm run check` after TypeScript changes.
- Name code with the interface's words: [the vocabulary glossary](scripts/vocabulary/GLOSSARY.md) is the vocabulary source for code, with its exceptions.
- Run `npm test` before handing off behavior changes.
- Use the smallest verification lane that can catch the failure you are working on; do not make an installer during every inner-loop UI change.
- Run `npm run desktop:prepare` after Electron, packaging, or runtime-resource changes, and before handing off a desktop-integrated change. The composed package and installer commands already include it.
- GitHub Actions is disabled in the canonical source repository (2026-09-30); pushes, PRs, and release tags do not run remote CI. The checked-in CI and source-tag workflows are dormant diagnostics and must not be re-enabled unless explicitly requested. Use local checks for development and the exact-commit local release lane for publication. `npm test` remains the complete local suite. Windows packaging and publication are inactive and must not gate Mac work.
- Before public Mac publication, run `npm run desktop:release:mac:check` on the final clean, committed release source on an Apple-silicon Mac with Node 24, supported npm, and Google Chrome installed for real CSS tests. It performs a fresh install, repository/TypeScript checks, the full application suite, and Electron preparation, then records the exact SHA, tree, build-input fingerprint, runtime, and successful stages in ignored `out/release-checks/local-verification.json`. Starting or failing a run invalidates the old receipt; source changes during checks fail. `-- --status` validates the saved receipt read-only. The full signed distribution build requires this receipt before starting. Publication requires a build begun after the receipt completed, the same Node/npm toolchain and dependency state, canonical pushed `main`, the matching annotated source tag, and source-bound signed artifact receipts before upload and immediately before publication. A shared per-worktree lock prevents local checks, all macOS builds, and publication from racing one another. It does not depend on GitHub Actions status; `desktop:release:mac:ci` remains an optional diagnostic.
- A pushed candidate tag is immutable evidence. Never move, reuse, or delete a failed candidate's tag; fix forward with a higher unique version, release commit, and tag. Before tagging, an ordinary local-check failure requires fixing the cause, committing, and rerunning local verification; it does not by itself consume a version.
- The Windows lanes (`npm run desktop:package:smoke`, `desktop:package`, `desktop:make:zip`, `desktop:make`) are dormant manual diagnostics; keep them out of CI, tags, and the release procedure unless Windows distribution is deliberately reactivated.
- On macOS, use Node 24 and run `npm run desktop:make:mac` for the complete ad hoc structural smoke candidate. That lane uses `AmpleFile Local Smoke` with a separate bundle id and updater-disabled runtime; never rename or install it over `AmpleFile.app`. Use `npm run desktop:rc:mac` for an app-only Developer ID-signed/notarized interactive candidate, `npm run desktop:make:mac:release` for the complete signed distribution candidate, and `npm run desktop:release:mac` for guarded build-and-publish. Inspect interrupted work with `npm run desktop:release:mac:status` and use a `:resume` lane only while its source-bound artifact checkpoint validates. Signing commands require the Developer ID identity and notarization profile documented in `docs/macos-release.md`.
- Finish release inputs and merge to `main` before the local release check, then build, tag, and publish. The check receipt pins the exact commit and cannot be carried across a merge, even with an identical tree. Do not edit source or run dependency installs while packaging. Use `desktop:release:mac:status` and a compatible `:resume` checkpoint from after the current successful check to avoid repeating completed signing and notarization. A fresh local check requires a subsequent fresh distribution build because it reinstalls dependencies. Release-tooling-only work needs focused and normal local checks, not a version bump or an Apple submission.
- When changing the kernel, AmpleFile agent, or CLI, run the kernel, adapter, protocol, broker, desktop-host, and packaging suites through `npm test`; add focused coverage for every new snapshot or command.
- Never commit provider keys, signing material, tokens, or generated user data.
- Reset the package version only immediately before the first public release candidate, as specified in the release runbooks, and never relabel an existing build or tag. Later fixes and rollback releases always use a higher unique version.
- The active public desktop lane is Apple-silicon macOS. Source commits and exact release tags belong in `Mat-Tom-Son/amplefile`; signed/notarized Mac artifacts and automatic updates belong only in `Mat-Tom-Son/amplefile-mac-releases`. The source repository does not need a GitHub Release for Mac publication. The legacy `Mat-Tom-Son/workspace` and `Mat-Tom-Son/workspace-mac-releases` repositories are frozen and must never receive AmpleFile commits, tags, artifacts, or updater metadata.
- Mac automatic updates preserve `com.amplefile.desktop` and `amplefile-desktop-updater`; the structural smoke uses `com.amplefile.desktop.local-smoke` and never contacts the production feed. Publish Mac artifacts only to `Mat-Tom-Son/amplefile-mac-releases` and do not create competing tag jobs.
- If an earlier ad hoc AmpleFile build causes repeated Keychain prompts, use `npm run desktop:reset:mac-safe-storage -- --yes --reopen` only after AmpleFile is fully quit. Never request the Safe Storage secret with `security ... -g`; that diagnostic can itself prompt. The reset may remove provider/restricted-app credentials but must preserve Connected Folders and ordinary app data.
- Keep README claims and the docs in sync with shipped behavior. In particular, do not claim native Google Drive, provider OAuth, package lifecycle controls, or public signing until the corresponding user path is verified.

The active verification and publication boundaries are documented in [macOS build and release lane](docs/macos-build.md) and [macOS release runbook](docs/macos-release.md). The dormant Windows references are retained in [Windows build](docs/windows-build.md) and [Windows releases and signing](docs/windows-release.md) for deliberate reactivation only. ## Bounded text Checks and folder observation

The built-in text-review Check accepts one reviewed `criteria` rubric and explicit primary/reference UTF-8 targets; it uses the AmpleFile agent's model without its transcript, general tools, or edits. Preserve quote/digest admission, source-pinned sensor authority, visible provider-use limits, and failure-as-health semantics. Desktop setup and CLI use the same Check service. Automation folder observation is an explicit declaration enabled by one receipted call, with bounded selectors, debounce, cooldown, and visible health. It pauses during Automation runs without replay and rebaselines after startup/wake unless v5 `ifMissed` catches up once; handoffs stay ordered steps in one Automation. Never make it an ambient or durable event bus. App `assistant.infer` reuses the same bounded model transport with its own instructions and no evidence admission; it is not a Check and never becomes one.
