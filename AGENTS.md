# AmpleFile contributor guide

AmpleFile is a local-first Mac app: a file manager around ordinary folders, with the native Pi agent runtime as each folder's Worker. Read [the product model](docs/product-model.md) before changing navigation, terminology, storage, trust, or Worker behavior; [the AmpleFile Agent and CLI](docs/amplefile-agent-and-cli.md) before changing the kernel, CLI, task registry, or an agent-facing adapter; [the act ledger](docs/act-ledger.md) before changing a product verb, prepared acts, receipts, or Recently Deleted; [Automations](docs/automations.md) and [the overview](docs/amplefile-agent-overview.md) before changing those; and [the collaboration contract](docs/collaboration-contract.md) before changing durable requests, delegation, questions, results, or waiting and continuation. Update these documents in the same change when their rules change.

## First visit

- Start with [Contributing](CONTRIBUTING.md) and the [development guide](docs/development.md) for setup, a source map, development profiles, and the right verification lane.
- Use Node 24 and npm 11.16.0 or newer (`.nvmrc`); npm must enforce the dependency-script policy described in [Contributing](CONTRIBUTING.md#prerequisites). With an older npm every npm command, `repo:check` included, fails with `EBADDEVENGINES`; upgrade npm rather than working around it. Run `npm ci`, then `npm run repo:check`; the latter also works before installation and never needs credentials or a network connection.
- `npm run local:dev` starts the browser UI on port 5173 (the only origin the local API accepts) and the local API; `/?fixture=connected-folder` and `/popover.html?fixture=agent` preview the UI from sample data without the API. `npm run desktop:smoke` starts unpackaged Electron after preparation. Use disposable folders for live work. The development app profile is separate, but Pi resources and Keychain need their own care; follow the development guide for explicit isolation.
- `npm run check` includes repository hygiene and TypeScript checks. Keep shared Skills, Claude symlinks, links, heading anchors, and documented npm commands valid; do not copy shared policy into a harness-specific file.

## Harness parity

- This `AGENTS.md` is the one canonical contributor contract. Codex reads it directly; Claude Code reads the root `CLAUDE.md`, which imports this file with `@AGENTS.md`.
- Edit shared policy here instead of copying it into `CLAUDE.md`, `.claude/`, `.codex/`, or harness-specific prose. Keep the root Claude entrypoint thin so the two harnesses cannot drift.
- Project-wide Skills have one source under the tracked `.agents/skills/` directory. Codex discovers that source directly; Claude Code gets the same Skill through tracked `.claude/skills/` symlinks. Never copy Skill contents between the two trees. All other `.claude/` and `.codex/` files are machine-local harness state, not contributor contracts.
- Both harnesses use the same checked-in npm scripts, documentation, test suites, and release lanes. Do not create Claude-only or Codex-only build or release commands.
- Native full-trust Skills, Extensions, built-in tools, and their catalog/runtime remain Pi-owned. AmpleFile owns the product documentation, which remains harness-neutral. Do not create a Codex-only or Claude-only catalog, wrapper format, prompt copy, or tool policy.
- `amplefile <command> --json`—for example, `amplefile context --json`—is the stable installed-product surface for any shell-capable harness: a content-free read lane plus a per-launch-authenticated act lane (`chat`, `chats`, `agent`, `history`, `files`, `search`, `connected-folders`, `tools`, `automations`, `recently-deleted`, `requests`, `jobs`, `worktrees`) that needs the running app. Every act verb executes on first call and returns a receipt; the lane has no approval, waiting, or authority-mode state. A task may be *waiting on an answer*: that is a state of its request record, not a held verb, and `chat wait`/`agent wait` settle on it and say so. The `agent` group talks to the AmpleFile Agent above all Connected Folders: machine-local transcript, Everywhere capabilities plus app-materialized instructions, the same turn machinery, full trust (taught to prefer the CLI, not tool-restricted). **Settings → Command Line** adds the command to Terminal and writes the outside-agent Skill for Claude Code or Codex. `npm run amplefile:drive` is the separate real-Pi-turn test driver; do not conflate it with the installed `amplefile` CLI.
- `npm run --silent amplefile:appearance` is the shared primitive for creating, resolving, and validating inert Connected Folder appearance proposals. It never applies a change; the person imports the typed file in Customize Connected Folder. `amplefile connected-folders appearance apply|reset|undo` is the act lane's receipted, undo-carrying path for the same typed proposal while the app runs. Keep its schema and safety boundary aligned with [Connected Folder customization](docs/connected-folder-customization.md).
- [Development](docs/development.md#agent-setup-and-shared-skills) links the Codex and Claude Code harness-loading docs. Repository behavior is defined here.

## Product language and boundaries

The interface's words are also the code's: identifiers, HTTP routes, CLI verbs and flags, JSON keys, schemas, and storage paths say **Connected Folder** (`connected-folder`, `connectedFolder`; the folder-backed working context), **Worker** (its AI helper), **AmpleFile Agent** (`amplefile-agent`; the agent above all Connected Folders), **Automation** (deterministic steps between Connected Folders), **Recently Deleted**, and **overview** (the AmpleFile Agent's digest). Labels are Title Case, and "Connected Folder" and "AmpleFile Agent" are capitalized everywhere, like "Worker"; an ordinary directory on disk stays a plain "folder". [The vocabulary glossary](scripts/vocabulary/GLOSSARY.md) lists the exceptions: opaque `space-<16 hex>` ids and the app-state `spaces/` and `management/` folders.

- Use **AmpleFile** as the user-facing product name.
- A **Connected Folder** is a human-friendly working context backed by one ordinary folder. Connecting an existing folder must not move, copy, or rename user files. AmpleFile maintains hidden, portable `.amplefile/connected-folder.json` identity metadata and `.amplefile/conversations/` logs in that folder.
- The folder is transparent infrastructure, not a proprietary container. Keep **Show in Finder** and normal filesystem interoperability intact.
- Use **Skills & Extensions**—the dialog the Action menu's **Skills & Extensions…** opens—as the user-facing management surface and **Capability** as the internal umbrella. Inside it, use **Skill** for a reusable way of working and **Extension** for executable Pi capabilities or connections. Packages are distribution and lifecycle plumbing, not another top-level product concept.
- Treat `src/shared/product-identity.json` as the single brand-bearing identity contract. The product is `AmpleFile`, the package is `amplefile-desktop`, the production app id is `com.amplefile.desktop`, the local-smoke app id is `com.amplefile.desktop.local-smoke`, the updater cache is `amplefile-desktop-updater`, the internal scheme is `amplefile-desktop`, the CLI is `amplefile`, and product-owned environment variables use `AMPLEFILE_*`.
- Product-facing technical contracts use `/api/connected-folders`, `/api/amplefile-agent`, `x-amplefile-session`, and `window.ampleFileDesktop`. Records use the identity fields `connectedFolderId`, `sourceConnectedFolderId`, and `targetConnectedFolderId`.
- Keep provider credentials, Connected Folder registrations, History objects, Pi sessions, ignore rules, and machine-specific application state outside user content folders. Only the documented portable `.amplefile/` records belong in a Connected Folder.
- Treat project Pi resources—including `.pi` and other Pi-supported project locations—as executable configuration. Creating or connecting a Connected Folder is AmpleFile's authorization to load that folder's local Pi configuration; disconnecting it revokes that authorization. Do not add a second trust prompt for the same act.
- Prefer Pi's built-in tools, resource loader, auth storage, model registry, package manager, skills, and extensions over app-specific replacements.
- [Extensions and computer work](docs/extension-foundation.md) records the shared integration design and inclusion requirements. Native Pi UI callbacks are transient, Chat-scoped interactions; never claim durable request continuation for a suspended callback, or auto-answer an Extension's confirmation. Included capabilities must use a supported path available to other Extensions too.
- Do not bundle proprietary tools, instructions, or source libraries.
- Do not describe a desktop-synchronized folder as native cloud integration. Google Drive works through Google Drive for desktop; direct Drive APIs and native provider OAuth are future adapter work.

## Product rails

- **Local first:** a Connected Folder remains useful as a folder without an account or cloud service.
- **Understandable:** explain outcomes in terms of Connected Folders and Skills & Extensions; identify Skills and Extensions inside that dialog, and reveal technical paths and package sources as supporting detail.
- **Explicit context:** connecting a folder, adding or copying materials, installing packages, granting connections, and attaching files are distinct actions. Do not silently put files or capabilities into a conversation.
- **Understandable authorization:** creating or connecting a Connected Folder authorizes its local Pi configuration without a redundant trust ceremony. Package review, connection secrets, and Chat context remain separate explicit acts, and disconnecting must revoke AmpleFile's project-runtime authorization.
- **Portable identity:** `.amplefile/` is data, not executable configuration. Preserve a valid manifest id when a Connected Folder's folder moves, hide `.amplefile/` and `.pi/` from the file list, and exclude both from History capture.
- **Fresh profile:** a new AmpleFile profile starts empty. Pi's global resources and auth may be shared at the configured Pi root, while AmpleFile sessions use their own `sessions/amplefile/` namespace. Disconnecting a linked Connected Folder leaves its folder in place; deleting a managed one moves its folder into Recently Deleted rather than erasing it.
- **Connected Folder–bound Chats:** every Chat belongs to one Connected Folder, and the panel shows the Chats of the Connected Folder shown. Never make a Chat silently inherit whichever Connected Folder happens to be selected.
- **Background continuity:** a Chat's accepted turn keeps running while another Chat or folder is shown. Switching, minimizing, sleep/wake recovery, and closing the last window must not cancel an accepted turn or lose its persisted result; only an explicit Stop or Quit may do that.
- **Settled deletion:** file, Chat, and Connected Folder deletion refuse while affected request work is unfinished, waiting on an answer, or still draining after Stop. File and Connected Folder deletion hold the shared active-work reservation through the effect. Deleting a managed parent requires disconnecting nested Connected Folders first; a pending deletion refuses new nested registrations. Never bypass a busy refusal with raw tools.
- **Native Pi compatibility:** preserve standard `SKILL.md` directories and Pi scopes. Do not fork an AmpleFile-only skill or extension format.
- **General computer work:** avoid code-only assumptions in primary UI copy and workflows.
- **Receipts, not gates:** every product verb executes on first call and leaves a receipt. Verbs that make bytes runnable, widen a standing power, or delete still pin their exact identities, journal before execution, recheck at effect time, execute at most once, and run through the same domain path as the desktop—as attribution and recovery, not as a gate. There is one authority mode and no approval card, standing rule, or toggle. Every destruction is reversible: History covers what it can, and everything it cannot goes to machine-local Recently Deleted with a retention window. Provider-secret entry is a setup surface rather than a model/CLI verb, and no task waits on it. See [the act ledger](docs/act-ledger.md#receipts-not-gates).
- **Requests, questions, and one result shape:** every accepted Worker or AmpleFile Agent turn belongs to a durable machine-local request record ([the collaboration contract](docs/collaboration-contract.md)). Agents hand each other one result shape—a plain-language summary, optional structured details, the files they chose, and an outcome of succeeded, partial, or failed—and ask a question instead of guessing. A question ends its own turn and one accepted answer continues it exactly once; a parent turn never sits on a child that is waiting, and the host starts at most one follow-up turn per settle batch within the request's limits. The same verbs serve the AmpleFile Agent, a Worker, and any shell-capable agent on the CLI, with the same receipts and the same named limits. Request records never enter a Connected Folder: what reaches a Worker Chat is its assignment, answers to its own questions, deliberately released payloads, and copied files.
- **Cadence above Connected Folders:** agency on a schedule lives in Connected Folders. Above them, only declared deterministic Automations run unattended, including explicitly enabled, bounded folder-change triggers ([Automations](docs/automations.md)). `automations enable` is one receipted call that pins the declaration digest; an Automation may message the AmpleFile Agent through its declared `agent` step and fill a closed set of host-resolved placeholders. Work across Connected Folders never runs inside a Worker Chat, because Connected Folder transcripts travel with the folder. Folder observation pauses during Automation runs without replay and takes a fresh baseline after startup or wake unless the declaration's `ifMissed` asks for one catch-up run; handoffs stay ordered steps in one Automation. Never make it an ambient or durable event bus.

## The window

The window is a file manager ([product model](docs/product-model.md#the-file-manager-window)): a sidebar of **Recents**, **Standard Folders**, and **Connected Folders** (nested ones indented under their parent), a Finder-style toolbar, the folder's contents, the path bar, and a right panel with **Info** and **History** tabs and the message box, where a Worker's Chat opens. Files, Chats, and History all belong to the Connected Folder shown. The toolbar's **Action** (⋯) menu and a Connected Folder's right-click menu offer Customize Connected Folder, Set Up for Me, Just the Look, **Skills & Extensions…**, Disconnect… (or Delete Connected Folder… for a managed one), and **Settings…**. The AmpleFile Agent lives in the menu-bar popover.

Settings has Appearance, AI Models, Automations, Command Line, Recently Deleted, Shortcut Keys, and About. Model-provider connections, model selection, API keys, and provider sign-in belong in **Settings → AI Models**; its scope is chosen with two large buttons—**This Worker**, naming the Connected Folder, and **AmpleFile Agent**—and its model is a searchable dropdown grouped by vendor. Provider credentials are machine-wide, while model selection is saved separately for each portable Connected Folder identity and for the AmpleFile Agent. Settings → Automations keeps its limits under a **Limits** disclosure, collapsed by default.

Skills & Extensions is a dialog like Settings, pinned to the Connected Folder it was opened from, with Installed and Discover views; package source, scope, type, load state, diagnostics, update, and removal stay visible inside it. Its Installed view starts with an **Included with AmpleFile** strip holding exactly the five included tools—Chrome, Computer Control, Web, Documents, and Service Connections—each with one Title Case status (Ready, Setup Needed, Unavailable, Not Checked, or Turned Off, with the per-tool variants in [Skills & Extensions](docs/skills-and-extensions.md)) and a **Set Up** pointer only when a person can act. Below the strip, **Everywhere** (the AmpleFile Agent and every Connected Folder) and **This Connected Folder only** (stored in the Connected Folder) sit side by side; a row opens its details on click. Its Add dialog asks **Where should it live?** first, then offers a Skill or pack (files) or a Pi package (source). A Discover details dialog shows the description, the where-chooser, the Skills and Extensions inside, one plain warning when the install can run code on the computer, and a collapsed **Technical details** section; install scripts and Extensions are disclosed before installation. Internal types may use `project`, `resource`, or `capability` as technical terms.

## AmpleFile Agent and CLI

- `AmpleFileKernel` is the shared in-process read authority for versioned Connected Folder context, registered Connected Folders, active turn and compaction tasks, and Pi capability snapshots. The renderer/local API and CLI must consume the same semantic source rather than recreate selection or catalog rules.
- Every query carries an explicit actor. An explicit Connected Folder id wins; otherwise context resolves to the deepest registered Connected Folder containing the actor's current directory; otherwise it resolves to none.
- Keep adapters thin. The CLI projection emits compact, content-free summaries, while domain services own mutations, trust, filesystem policy, History, and concurrency controls.
- Protocol v1 under `~/Library/Application Support/AmpleFile/cli` is same-user coordination, not an authenticated caller boundary. It must remain read-only and content-free. Mutations belong only to the separately versioned act lane, which requires the per-launch act token minted by the running interactive app, explicit `--connected-folder` selection on every Connected Folder–scoped write (the `agent`, `automations`, `recently-deleted`, and `requests` families take none; a Recently Deleted entry records its source Connected Folder, and a request record pins the Connected Folder of each child when work is handed over), replayed-request protection, and a durable receipt per accepted action. Runnable-code, standing-power, and destruction verbs run immediately through the prepare, pin, journal-first, fenced execution path and return the receipt like any direct verb; failed or interrupted executions are never auto-retried. The act facade cannot enter secrets; the act token and provider credentials have no act verb.
- Start and finish kernel task records on every turn and Chat-compaction path, including errors and abort cleanup. Never leave ghost tasks or let a capability mutation interrupt active work.
- The AmpleFile Agent's menu-bar popover is a separate sandboxed renderer with a dedicated narrow preload. Its attachments are bounded references, not copies; downstream `chat.send`, `files.add`, and Connected Folder create/register actions carry an explicit active AmpleFile Agent parent task id. Never infer request lineage from whichever turn happens to be running, and never report a request Done while a child is running, waiting on an answer, failed, lost, or stopped.
- Every accepted turn joins one durable request record under the state root's `requests/` directory. Records survive restart, are reconciled against the turn journal and never re-dispatched, keep their questions and results by id, and are removed only by retention. `requests list|show` reads that graph; `chat report|ask|answer|handoff` write to it; `chat wait`/`agent wait` settle when the followed turn ends or when its task starts waiting, and say which. Delivery of a report, an answer, or a handoff is host-side and needs no AmpleFile Agent turn.
- Treat snapshot versions and `--json` output as compatibility contracts. Update implementation, adapters, tests, [the AmpleFile Agent and CLI guide](docs/amplefile-agent-and-cli.md), README, security, and privacy documentation together when they change.

## Development

- Develop with Node 24 and npm 11.16.0 or newer; the package runtime floor is Node 22.19.0.
- Run `npm run check` after TypeScript changes, and `npm test` before handing off behavior changes. When changing the kernel, AmpleFile Agent, or CLI, add focused coverage for every new snapshot or command.
- Name code with the interface's words: [the vocabulary glossary](scripts/vocabulary/GLOSSARY.md) is the vocabulary source for code. `node scripts/rebrand/inventory.mjs --check` fails if a name from the earlier app comes back.
- Docs describe how AmpleFile works today. Say what is true now, not what changed or when; keep README claims and the docs in sync with shipped behavior. Do not claim native Google Drive, provider OAuth, package lifecycle controls, or public signing until the user path is verified.
- Use the smallest verification lane that can catch the failure you are working on; do not make an installer during every inner-loop UI change.
- Run `npm run desktop:prepare` after Electron, packaging, or runtime-resource changes, and before handing off a desktop-integrated change. The composed package and installer commands already include it.
- Never commit provider keys, signing material, tokens, or generated user data.

## Releases

- AmpleFile ships for Apple-silicon Macs only. Source commits and exact release tags belong in `Mat-Tom-Son/amplefile`; signed and notarized Mac artifacts and automatic updates belong only in `Mat-Tom-Son/amplefile-mac-releases`. The source repository needs no GitHub Release.
- GitHub Actions is off in the source repository; pushes, PRs, and tags run no remote CI. The checked-in workflows are dormant diagnostics; do not re-enable them unless asked. `npm test` is the complete local suite.
- Before public publication, run `npm run desktop:release:mac:check` on the final clean, committed release source on an Apple-silicon Mac with Node 24, supported npm, and Google Chrome installed for real CSS tests. It runs `npm ci`, `npm run check`, `npm test`, and `npm run desktop:prepare`, then records the exact SHA, tree, build-input fingerprint, runtime, and stages in ignored `out/release-checks/local-verification.json`. Starting or failing a run invalidates the old receipt; source changes during checks fail. `-- --status` validates the saved receipt read-only. The signed distribution build requires this receipt. Publication requires a build begun after the receipt completed, the same toolchain and dependency state, canonical pushed `main`, the matching annotated source tag, and source-bound signed artifact receipts before upload and immediately before publication. A per-worktree lock keeps checks, builds, and publication from racing. `desktop:release:mac:ci` is an optional diagnostic.
- Finish release inputs and merge to `main` before the release check, then build, tag, and publish. The check receipt pins the exact commit and cannot be carried across a merge. Do not edit source or run dependency installs while packaging. A fresh release check requires a fresh distribution build, because it reinstalls dependencies. Release-tooling-only work needs focused and normal local checks, not a version bump or an Apple submission.
- A pushed candidate tag is immutable evidence. Never move, reuse, or delete a failed candidate's tag; fix forward with a higher unique version, release commit, and tag. Never relabel an existing build or tag. An ordinary local-check failure before tagging does not consume a version.
- Use `npm run desktop:make:mac` for the ad hoc structural smoke candidate. It builds `AmpleFile Local Smoke` with the separate bundle id `com.amplefile.desktop.local-smoke` and an updater-disabled runtime that never contacts the production feed; never rename or install it over `AmpleFile.app`. Use `npm run desktop:rc:mac` for an app-only Developer ID-signed and notarized interactive candidate, `npm run desktop:make:mac:release` for the complete signed distribution candidate, and `npm run desktop:release:mac` for guarded build-and-publish. Inspect interrupted work with `npm run desktop:release:mac:status` and use a `:resume` lane only while its source-bound checkpoint validates. Signing needs the Developer ID identity and notarization profile in [the release runbook](docs/macos-release.md).
- Automatic updates keep `com.amplefile.desktop` and `amplefile-desktop-updater`. Publish only to `Mat-Tom-Son/amplefile-mac-releases`, and do not create competing tag jobs.
- If an ad hoc AmpleFile build causes repeated Keychain prompts, use `npm run desktop:reset:mac-safe-storage -- --yes --reopen` only after AmpleFile is fully quit. Never request the Safe Storage secret with `security ... -g`; that diagnostic can itself prompt. The reset may remove provider credentials but must keep Connected Folders and ordinary app data.

[macOS build lanes](docs/macos-build.md) and [the macOS release runbook](docs/macos-release.md) document verification and publication. [The AmpleFile Agent and CLI](docs/amplefile-agent-and-cli.md) documents the control-plane boundary and the real-agent driver.
